# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Layout

The git root is this folder. The Home Assistant add-on lives in `ems/` (manifest `ems/config.yaml`), and the root `repository.yaml` lets the HA add-on store find it. Commands run from the repo root unless noted. Paths without a prefix are relative to `ems/`.

## Commands

Build the front end. This is required on a fresh clone: `bin/build.mjs` writes everything the pages load to `app/public/assets/build/` (gitignored): `app.css` (lightningcss bundle of `app/assets/css/app.css`), `app.js` (esbuild bundle of `app/assets/js/main.js`), the icon sprite `icons.svg`, `InterVariable.woff2`, `favicon.svg` and `manifest.json` with content hashes for `asset()`.

```sh
cd ems && npm install && npm run build
```

Run locally. The PHP app never reads `.env` (only `docker compose` does), so pass the variables inline or export them. Alternatively, enter URL and token in the setup wizard, which writes `data/connection.json`.

```sh
EMS_DATA=./data HA_URL=http://<ha-host>:8123 HA_TOKEN=<token> php -S 127.0.0.1:8099 -t ems/app/public ems/app/public/router.php
EMS_DATA=./data php ems/bin/recorder.php   # second process: sessions, forecast memory, calibration
```

Demo mode needs no Home Assistant. `DemoModel` simulates a plant from `app/demo/beispieldaten.json` (regenerate with `npm run demo:data`), `DemoHaClient` answers in place of `HaClient`, and `/api/live` advances the running session because no recorder runs. `EMS_DEMO_CLOCK=HH:MM` freezes the live clock. `/komponenten` (component gallery) only exists in demo mode.

```sh
EMS_DEMO=1 EMS_DATA=/tmp/ems-demo php ems/bin/demo-seed.php   # fresh demo database, never /data
EMS_DEMO=1 EMS_DATA=/tmp/ems-demo php -S 127.0.0.1:8099 -t ems/app/public ems/app/public/router.php
```

Docker runs php-fpm, nginx and the recorder in one container on port 8099 (`.env` via compose, `./data` mounted at `/data`):

```sh
docker compose up --build
```

Checks:
- `php ems/bin/selftest.php` is a hand-written script of `check(bool, 'German message')` calls. It exits 1 at the first failing check, so single cases cannot be selected. It covers pure logic in `Energy`, `Forecast`, `WeatherFeed`, `Series`, `Sessions` and the helpers, not HTTP routes, HA calls or JavaScript. Two extra checks run only if `/tmp/MOSMIX_L_LATEST_F9519.kmz` exists.
- `cd ems && npm run check:contrast` checks every token color pair in light and dark against WCAG AA.
- `cd ems && npm run check:ui` seeds its own demo database, starts a PHP server on port 8198 and drives the installed Google Chrome through playwright-core. Per page it checks 360 to 1920 px in light and dark: no horizontal scroll and no element over the edge, no clipped labels, hit areas of at least 44 px, Inter loaded, no foreign requests, no CSP or console errors, axe `wcag22aa` on the page and on every dialog, no endless animation with reduced motion, and at 320, 360 and 390 px with 100 and 115 % root font size that neither the page nor any sheet has an element over its edge. Screenshots go to `ems/tests/screenshots/`. `CHECK_ROUTES=/,/speicher` limits the pages, `CHECK_SHOTS=0` skips screenshots, `CHECK_TARIFF=dynamic` switches the demo to the dynamic tariff with Netzladen „In Ladefenstern“ and a price range, so the windows and the window choice get checked too (with the static tariff of the seed they do not exist).

No linter is configured; use `php -l <file>` for syntax.

Debugging: `EMS_DEBUG=1` shows PHP errors. Recorder exceptions go to `$EMS_DATA/recorder.log`, not the console.

Release: bump `version` in `ems/config.yaml`. The Supervisor compares that number to offer updates.

## Architecture

The app reads a PV system, a home battery, a grid meter and a go-e wallbox through Home Assistant entities the user maps in the setup wizard. It computes the energy flow, a charging suggestion and a PV forecast itself. With the master switch (`cfg.control.active`, default off) it controls the go-e like evcc (`Controller`, below), the battery's backup buffer (`Reserve`) and, opt-in, charging the battery from the grid in charging windows (`BatteryPlan`). With the switch off it writes nothing, except the backup-buffer default when the user saves it. Push notifications (`Notify`, below) are independent of the switch.

**Two processes share one SQLite file** (`$EMS_DATA/ems.sqlite`, WAL mode):
- **Web:** `app/public/index.php` is a single front controller with an if-chain router and no framework. `page()`/`render()` render `app/views/<name>.php` into `app/views/shell.php`. JSON endpoints: `/api/live` (live payload), `/api/series?chart=…` (data for the SVG charts, including `chart=price`), `/api/entities` (entity search), `/api/config.json` (export), and the writes `/api/modus` (`mode` and/or `grid`), `/api/limit`, `/api/darstellung`, `/api/grenzen` and `/api/mitteilung` (test notification; CSRF token as `_csrf` in the JSON body; `ingest_json_body()` maps it to `$_POST`).
- **Recorder:** `bin/recorder.php` loops every 10 s: `WeatherFeed::refresh()`, `MarketPrices::refresh()` (own try/catch), `Snapshot::build()`, `Sessions::tick()`, `GridMeter::record()`, `Controller::tick()`, `ProviderControl::sync()`, `Reserve::sync()`, `BatteryPlans::refresh()`, `BatteryPlan::sync()`, `Notify::tick()` (own try/catch), `Tariff::recordProvider()` and `Tariff::syncStaticPrice()` every 5 min, `ChargePlan::refresh()`, and `Series::calibrate()` once a day from 01:00. In Docker, `docker/start.sh` runs both as root so the shared SQLite file works.

**Pages:** six tabs, `/` (Laden), `/speicher`, `/prognose` (with `/prognose/strompreis`; `ui_seg_links()` switches Sonne | Strompreis), `/ladevorgaenge`, `/statistik` and `/einstellungen/{bereich}` (gear icon, short label „Optionen“; the master switch card `partials/ems-switch.php` on top, then nine areas, one view each in `app/views/einstellungen/`), plus the wizard `/einrichten/{schritt}`. Second-level content opens in native `<dialog>` sheets. The old routes `/laden`, `/batterie` and `/mehr/*` redirect; `/statistik` is the heatmap page again (it once redirected to Ladevorgänge, POSTs there still reach the sessions actions). Forms post to `/einstellungen` with `section` and `back` (`/mehr` still accepts posts from old pages); `Actions::saveSettings()` only changes the fields a form sends; with `Accept: application/json` (`wants_json()`) the notify sections answer JSON instead of redirecting.

**Storage:** `ConfigStore` wraps the database. Table `kv` holds settings as JSON (`mapping`, `plant`, `charge`, `battery_strategy`, `tariffs` incl. `co2_g_kwh`, `vehicle`, `chargepoint`, `weather`, `ui`, `wizard_done`) plus `control` (master switch) and operational keys such as `control_state`, `control_kick`, `control_heartbeat`, `charge_target`, `charge_target_done`, `reserve_guard`, `notify_state`, `notify_slug`, `house_mean`, `vehicle_repair`, `modes_v2` and `modes_v3` (the one-off mode migrations below are done), `tariff_history`, `market_meta`, `grid_meter`, `charge_plan`, `grid_target` (the car's target for Netzladen), `grid_choice` (the windows chosen for the car), `grid_done`, `price_windows` (charging window settings), `grid_plans`, `grid_plan_done`, `grid_plan_armed`, `battery_plans`, `battery_plan_state`, `battery_plan_done`, `battery_plan_armed`, `provider`, `provider_state`, `grid_now_target`, `charge_rate`, `year_prices` (daily prices of the last 365 days for the yearly check), `pvgis` (PVGIS yield of the plant), `ha_location`, `battery_boost` (the one-time energy boost before 1.24) and `battery_grid` (its switching state); `house_mean` holds the hourly house profile; `notify` holds the notification settings, including the custom notifications (`custom`). Defaults are in `ConfigStore::defaults()`; read them through `cfg()`. Other tables: `stat_cache` (HA statistics of finished periods for the heatmap, one week), `sessions` (charging sessions), `daily` (actual vs. model kWh per day, `model_mode`), `forecast_days`, `forecast_issues` (every DWD run is kept), `weather_hours` (800 days), `notifications` (the last 200 sent), `market_prices` (day-ahead price per quarter hour, hours before October 2025, EUR/MWh net), `provider_prices` (what the provider entity reported, ct/kWh gross) and `grid_quarters` (grid import and export per quarter hour, measured by EMS). Also in `$EMS_DATA`: `connection.json` (URL and token, mode 0600) and `states-cache.json` (3 s cache of all HA states).

**Setup gate:** until `wizard_done` is set, every page redirects to `/einrichten/…`, shown without navigation. `/api/*` answers regardless.

**Home Assistant:** `ha()` returns a `HaSource`: `HaClient`, or `DemoHaClient` in demo mode (which also has Octopus-like switches `switch.demo_octopus_smart_control`/`_boost_charge`). `connection()` in `helpers.php` uses the Supervisor proxy when `SUPERVISOR_TOKEN` is set (`http://supervisor/core`). Otherwise `HA_URL`/`HA_TOKEN` apply, and `connection.json` fills what is missing. `HaClient` uses REST for states and history; its writes are `setNumber()` and `service()`, limited to `number`/`input_number.set_value`, `select`/`input_select.select_option`, `button.press` and `switch`/`input_boolean.turn_on`/`turn_off`, plus `notify()` for `notify.<service>` (`notifyServices()` lists them from `/api/services`). Statistics go through a hand-written WebSocket client (`recorder/statistics_during_period`), since REST does not expose them. `Actions::SUGGEST` holds default entity IDs from the author's installation (sonnenbatterie and go-e). They are only suggestions.

**Energy and charging** (`Snapshot::build()` calls into `Energy`):
1. Mapped entities are read and converted to kW/kWh. A missing unit is read as W, with a warning.
2. `Energy::balance()` gives the house base load (minus the wallbox if the house meter includes it) and the inflows and outflows. Surplus = PV − house − battery charge, where the battery term applies only while SOC is below the priority threshold. `Energy::flowBar()` turns the values into the bar segments and the bracket spans; sources and sinks are each scaled to their own total, so both bracket rows always span the full bar even when the meters disagree. `Energy::flowGraph()` feeds the alternative "Energie-Flow" (`ui_energy_flow()`, `components/energy-flow.js`, payload `flow_graph`), laid out Rein → Raus: sources sun, battery and grid on the left, sinks house, car, battery and export on the right, one link per source and sink (`sun_car`, `grid_home`, …). Sun goes first to consumption, then the battery, the rest to the grid; the battery and then the grid cover the rest, split between house and car by their share. The sun node carries today's forecast progress (`Snapshot::flowForecast()`). `Snapshot::flowGraph()` builds it for Laden, `/api/live` and the live preview under Einstellungen → Darstellung and adds the second line under each name: battery `to_full_kwh` (`Energy::toFull()`), house `mean_kw` (usual load), grid and export `price_ct` (tariffs), car `range_km`. The script measures the circles and draws the links into an SVG overlay, so the layout is plain CSS. Line width, dot spacing and speed follow each link's share of the total input (`--ef-gap`, `--ef-dur` via CSSOM, the keyframes read the variable); every sink node carries its own `mix` for the ring. Which one Laden shows is `ui.flow_view` (`bar` or `graph`). Both sit outside a card; `ui_flow_table()` puts Rein and Raus in a card below.
3. `Energy::suggest()` picks a target for the modes in `Energy::MODES`: `aus`, `smart`, `smart_dauerhaft`, `schnell` and `netz` (shown as Aus, Intelligent, Min+Sonne, Schnell, Netzladen; `Energy::fullPower()` is true for the last two). `charge.mode` holds only `aus` (the „Laden“ switch in the card) or one of `Energy::SUN_MODES`, with `charge.last_mode` for switching back on; `netz` only comes from `charge.grid` (`off`, `now`, `windows`) through `ChargePlan::effective()`: 0.23 kW per A, 6–16 A, 1 or 3 phases. It follows the battery zones of `Energy::zone()` from `battery_strategy`: below `priority_soc` the battery charges first (`house`), above it the car gets the surplus (`car`), from `car_buffer_soc` the battery may hold a running charge (`boost`), from `car_auto_soc` charging starts without sun (`start`). A limit of 100 % switches `boost` and `start` off. `Energy::allot()` splits the result physically: sun to the car first, the rest of the surplus to the battery (capped at its current charge while exporting) and the grid. Whatever the car still lacks comes from the battery down to the backup buffer (`battery_strategy.backup_soc`), capped by `discharge_kw` minus what the house already draws, and then from the grid. With an unknown `discharge_kw`, Schnell shows it as battery-then-grid (`mixed`). Netzladen takes it from the grid only, as long as the backup buffer can be raised (`Energy::batteryFor()`, `Reserve::settings()['active']`: entity and default set). Until 1.9, `schnell` meant Netzladen and `battery_strategy.grid_protect` switched the protection; `ConfigStore::migrateModes()` rewrites stored modes once (`charge.mode`, `charge.after_unplug`, `control_state.mode`, `notify_state.mode`: `schnell` with protection becomes `netz`, without it stays Schnell) and drops `grid_protect`; `applyPortable()` does the same for exports with `version` below 2 (`Energy::migratedMode()`). Since 1.13 `ConfigStore::migrateGrid()` (`kv.modes_v3`) turns a stored `netz` into `smart` with `grid` `now` once, `after_unplug` `netz` into keep, and drops `price_limit_ct`; `applyPortable()` does the same for exports below version 3.
4. `Controller` turns that into the wallbox state like evcc (`core/loadpoint.go`): `step()` is pure and keeps timers on conditions (enable after `on_delay_s`, 60 s; disable after `off_delay_s`, 180 s, holding the minimum current meanwhile; 1p→3p after the enable delay, 3p→1p after the disable delay; `switch_s` as minimum gap between switches), truncates to whole amps, locks the charger without a car and lets PV start at once after plugging in. `aus`, `schnell` and `netz` act immediately. `tick()` (recorder every 10 s, a step every 30 s or after `control_kick`) also runs `Target::check()`. `apply()` writes only differences and only when the switch is on: `frc` on/off, `amp`, `psm` 1p/3p, ordered so power never overshoots. The car status of both go-e integrations is read through `Sessions::carState()` (charging, waiting, complete, idle, error; syssi reports `wait_for_car`, marq24 a text in the HA language such as „Warte auf Fahrzeug“ or „Wait for car“, its code sensor 0–5, the go-e's own MQTT entities `WaitCar`), which `carConnected()`, the vehicle view, sessions, notifications, the backup buffer and the controller use. Select values are handled by meaning (`Controller::OPTIONS`, `meaning()`, `option()`): the write takes the matching option from the entity's `options` attribute, so both marq24's „go-eCharger API v2“ integration (`2`/`1`/`0`, `1`/`2`, local HTTP API, the author's setup for writing) and the syssi MQTT integration (`charge`/`dont_charge`/`neutral`, `one_phase`/`three_phases`) work. The author's go-e Charger PRO (firmware 60.4) ignores MQTT set commands even with `mcr` off, so writes go through marq24. A reported value that differs from the written one after 60 s counts as a foreign write if the wallbox had reported the written value in between (`observe()` marks `seen`, also between steps) or shows a third value; if it never took the value and still reports the old one, the write was ignored (`ignored`, e.g. a go-e that does not take MQTT commands). A write whose value is no longer wanted (the mode changed and the wallbox already reports the new target) is dropped instead of counted. Three of either in ten minutes pause control (`paused`), with the hint matching the more frequent case. Turning the switch off writes `frc` 0. `Snapshot` reads the controller state; without a fresh step it computes a preview step without saving.

`Snapshot::timerView()` gives the running wait of the controller (on or off delay, phase switch, contactor guard) with label, what follows, why (`why`), remaining and total seconds as `chargepoint.timer`; the card shows it above the session overview with a thin bar and `components/chargepoint.js` counts it down every second between polls. It is only shown while EMS really controls (master switch on, not paused; otherwise the recorder's steps are display-only and their timers fictional), the off delay only while the car draws power, the on delay not when the car reports complete. The session overview (`Snapshot::sessionView()`, `snap.day_group`) shows, like the Ladevorgänge list, the cycles of today from the first cycle's start to the end of the last, „seit …“ while one runs; a cycle still running from yesterday names the day. „Geladen“ in the card is the running cycle (`Snapshot::cycleKwh()`, `chargepoint.cycle_kwh`; without one the cycle that ended today while the car is still plugged in, else 0), like Leistung and Restzeit; `chargepoint.session_kwh` (the go-e counter or the plug-in's cycles) stays „since plug-in“ for targets and notifications. Restzeit is the car's own value when `mapping.car_time_full` is mapped (`Energy::durationSeconds()`, unit h/min/s, none = min), else `Energy::timeToLimit()` (needs car SOC, `vehicle.capacity_kwh` or `car_capacity`, power); `chargepoint.remaining_hint` names what is missing („Akku fehlt“, „Ladestand fehlt“), „vom Auto“ or „bis zum Ziel“.

`Snapshot::control()` turns the controller decision (with countdown) and the suggestions of the four charging modes into the "Regelung" card under the charge point (`ui_control()`, `components/control.js`, live payload key `control`). The modes and the calculation sit in a `<details>` that starts closed.

`Reserve` owns the backup buffer (`mapping.battery_reserve`, a number entity). Saving under Einstellungen → Speicher writes the default (`backup_soc`). `Reserve::sync()` runs in the recorder, after `/api/modus` and in demo mode from `/api/live`; it only raises while the master switch is on. In `netz` it raises the buffer to the current SOC while the car charges (never to 100 %, so the battery has nothing to recharge from the grid), keeps it raised while the session stays open, and restores the default after a mode change, the session end or unplugging. State, errors (retry after 60 s) and the last steps live in `kv.reserve_guard`. `Reserve::decide()` is the pure decision. The sonnenbatterie number entity reports 0 until it is first written, so the app keeps the default itself.

`Target` holds charge targets per plug-in (the sheets offer energy, time or SOC; the SOC slider shows the estimated range through `rangeAt()` in `components/target.js`, range per percent of now, else capacity and consumption; a stored `range` target still works and the sheet shows it as SOC): one for Sonne & Speicher (`kv.charge_target`, with a follow-up mode) and one for Netzladen (`kv.grid_target`, `then` is `grid`, optional `ready_by`; `Target::get($store, 'grid')`, `build(…, 'grid')`). Each is energy since plug-in, a time, the car's SOC or its range (`range`, needs `vehicle.range_km`). With a consumption (`Energy::consumption()`: `vehicle.consumption_kwh` in kWh/100 km, else derived from range, SOC and capacity) every target view names the km (`Energy::kmFromKwh()`, 8 % loss as `Energy::CHARGE_EFFICIENCY`), and so does the session overview; `components/target.js` computes the same hints while typing in the sheet. `Target::check()` (from `Controller::tick()`, which then recomputes the mode with `ChargePlan::effectiveNow()`): the Sonne & Speicher target switches to its follow-up mode (`charge.then_mode` as default, `aus` stops the wallbox); the Netzladen target turns „Jetzt“ off, or for „In Ladefenstern“ sets `kv.grid_done` and clears `grid_choice` (no window charging until unplugged), and the solar mode goes on. Unplugging clears both targets, `grid_choice` and `grid_done`, turns „Jetzt“ off and applies `charge.after_unplug` if set. Both are set from sheets in the charge point card (`partials/target-form.php` with `$scope`, `section=target`, `scope`); the IDs carry the scope because both sheets share the page. `Target::neededKwh()` gives what is still missing at the wallbox, with charging loss.

`ProviderControl` covers tariffs where the provider plans the car's charging (Octopus Intelligent): `kv.provider` (`on`, `window` tariff = the static tariff's car windows, or time with `from`/`to`), `mapping.provider_boost` (Boost Charge) and `mapping.provider_control` (Smart Control), section `provider` under Einstellungen → Ladepunkt (`view()` with the next change). Inside the window `ChargePlan::effective()` (last argument `$provider`, after „Jetzt“) frees the wallbox as `netz` with reason `provider` (Snapshot shows „(Anbieter)“ and the card's grid text says until when), so the backup buffer is raised like Netzladen. `sync()` (recorder, demo `/api/live`, only with the master switch) turns Smart Control on when it is off (at most every 15 min, `control_at`), then Boost Charge off inside the window and on outside (`wantBoost()`; on also inside while „Jetzt“ runs), writing at a window change, at plug-in, or every 15 min while it differs (on only with a plugged, not complete car, since Octopus ends a boost by itself); state and log in `kv.provider_state`.

`ChargePlan` handles Netzladen for the car (`charge.grid`: `now` while „Jetzt“ runs, else `windows` or `off` after the card's switch „Ladefenster nutzen“, `charge.grid_windows`, null = derived from `grid` for old configs; `windowsWanted()`, `afterNow()`). „Jetzt“ only starts from its own target sheet (`Target` scope `now`, `kv.grid_now_target`, `section=target` `scope=now`; `/api/modus` refuses `grid=now` without it, `grid=stop` and `Actions::stopNow()` end it, `windows=1|0` is the switch); reaching that target or unplugging returns to `afterNow()`. `GridPlans` holds the weekly Ladepläne (`kv.grid_plans`, at most 10: `days` 1–7 (none preselected for a new plan), `time`, `type` soc/energy with `value` (`range` from older plans still plans, the sheet shows it as SOC), optional `soc_below` (home battery), `pv_below` (forecast kWh until the time) and `car_below` (the car's SOC, slider with range; `car_below_type` range only from older plans) as conditions; once they hold with the car plugged in, `GridPlans::armed()` keeps the plan for that time (`kv.grid_plan_armed`, `<id>@<deadline>`, cleared on save), so charging past the car's limit does not stop it; a soc target above the limit the car reports (`car_limit`) ends at that limit, since EMS never writes the car's limit; `section=grid_plan`, sheets `partials/plan-form.php`, one per plan plus `cp-plan-new`, conditions stacked with their limit shown by `:has()` only when switched on; the card lists each plan as `GridPlans::headline()` (goal and time) over `Snapshot::planRows()` `detail` (days, `nextText()` without repeating the time, `conditionsShort()`); `components/plan.js` computes from its `data-*` (next midnight per weekday, hourly PV forecast, power, price, car values) the approximate start, the cost and the PV forecast per chosen day until the time). The card hides „Ladefenster nutzen“ with a static tariff. `refresh()` plans for the windows' target with `ready_by` first, else for the next enabled plan whose time is within `GridPlans::HORIZON_S` (24 h) and whose conditions hold (`source` `schedule`, `plan_id`); with a static tariff all prices are equal, so `plan()` takes the latest quarter hours. A reached plan is done until its next time (`kv.grid_plan_done`). `effective()` charges `netz` with reason `plan` in a schedule plan's quarter hours regardless of the windows switch and tariff. `powerKw($charge, $carKw)` is the smaller of wallbox (max current × phases) and car: `vehicle.charge_kw` or the rate `GridPlans::learn()` averages once a minute while charging in `netz` (`kv.charge_rate`, `learned()` from 5 samples). `effective()` turns the user mode into `netz` with `now` (reason `now`), or with `windows` inside a window the user chose in the card (`kv.grid_choice`, `ChargePlan::chosen()`, saved by `section=grid_windows` from `PriceWindows::offered()`; reason `window`) or a quarter hour the plan added (`plan`), until `kv.grid_done`; `aus`, an unplugged car and a static tariff never charge in windows. `plan()` is pure: for a Netzladen target with `ready_by` it counts the chosen windows' quarter hours before the deadline at full power (`powerKw()`: max current × phases) plus the expected sun between them (forecast minus the usual house load, 70 %, only in `smart` and `smart_dauerhaft`), and if that is not enough adds the cheapest other quarter hours (`extra`, later ones first on equal prices); status `windows`, `sun`, `ok`, `partial` (part waits for tomorrow's prices), `waiting`, `tight` (every quarter hour), `done` or `unknown`. `refresh()` (recorder, demo `/api/live`, after saving a target or the window choice) stores it in `kv.charge_plan` only with `grid` `windows`, a dynamic tariff, a Netzladen target with `ready_by` and a car, and replans every 15 min or when target, horizon (`Tariff::horizon()`), mode or the chosen slots change. `Snapshot::finish()` writes `effective_mode` and `effective_reason` into `cfg.charge` of the snapshot and builds the suggestion and the controller preview with it; `Controller::tick()` and `Reserve::sync()` read `effective_mode`, so the buffer is raised like in Netzladen. `Snapshot::gridText()`, `windowChoices()` and `chargepoint.grid_windows` fill the Netzladen section of the card: the grid target row and the checkbox form of windows (`data-grid-show`, toggled by `components/chargepoint.js`, which posts `mode` or `grid` to `/api/modus`; `grid` `windows` is refused with a static tariff).

`PriceWindows` (kv `price_windows`: `length_h`, `off` days, `range_from`/`range_to` and `range_off`, `custom` windows) lists, up to `Tariff::horizon()` (spot or the recorded provider prices of Tibber or Octopus, whichever reaches further), the cheapest contiguous window of `length_h` hours per calendar day from the dynamic price (`cheapest()`, earlier first on ties), every run of quarter hours inside the price range (`runs()`, kind `range`, switched off by start), and custom windows. They only count with a dynamic tariff (`enabled()`); `offered()` gives the active ones still to come for the car and the battery, `at()` and `slotsOf()` work on any list. With a static tariff they are hidden everywhere (Prognose → Strompreis shows only a hint, the card has neither the switch nor the link). Sections: `windows` (length), `window_range`, `window_toggle` (by `day` or, for range windows, `start`), `window_add`, `window_delete`. The price chart (`chart=price`, also over provider-only quarter hours) carries `bands` (kind `window` or `extra`, the plan's `extra` only with a dynamic tariff) and `ranges` (the price range as a horizontal band), both empty with a static tariff. The chip `[data-chart-bands]` in the chart tools, only rendered with a dynamic tariff, shows or hides them (`state.bands` in `charts/time.js`).

`BatteryPlans` holds the battery's Ladepläne, the same for static and dynamic tariffs (`kv.battery_plans`, at most 10: `when` window or time, `once` or `days`, `time`, `amount` soc or need, `target_soc` (target, or the cap for need), `start` late or early, optional `soc_below`; plans from 1.23 read as time and soc; `section=battery_plan`, sheets `partials/battery-plan-form.php` with `components/battery-plan.js`, CSS `:has()` hides what does not apply, listed under Speicher → Ausblick with `rows()` and `text()`). `windows()` gives the cheap windows: static the tariff's windows `for` battery on their weekdays (over midnight from the start day), dynamic `PriceWindows::offered()`; `occurrence()` the next one for a plan (window by the weekday it starts, `once` any day, time via `GridPlans::next()`, the done end skipped). `refresh()` (recorder and demo `/api/live`, every 15 min or when plan, occurrence or price horizon change; removes a `once` plan whose occurrence is over or done) takes the plan whose occurrence ends first within 24 h, checks `soc_below` (latched in `kv.battery_plan_armed`), for `need` runs `BatteryPlan::decide()` (charge once to its target, then the battery serves the house; `reason` other than charge becomes `enough`, `price` or `done`; early plans charge to its `target_soc`, late ones to its `end_soc`) and then the pure `schedule()`: quarter by quarter until the end the battery gains sun (forecast × 0.7 minus the usual house load), the house drains it down to the backup buffer, and planned quarters charge at `grid_kw × efficiency`; it adds quarters allowed in the window (late: cheapest at the battery price, ties later first; early: earliest) until the level is reached (`reach` peak for early: once, capped at the target; end: at the deadline, `stop_kwh` is the peak the charging needs) (`ok`, `tight`, `sun`, `done`, plus `skip`/`unknown`), stored in `kv.battery_plan_state` with `stop_soc`. `current()` gives the running slot run (target `stop_soc`), which `BatteryPlan::sync()` charges (`state.source` plan, or boost for a leftover `kv.battery_boost` from before 1.24, which wins); reaching the target marks the plan done until its next time (`kv.battery_plan_done`, state status `done`). `GridPlans::sheetData()` feeds both plan sheets (day starts, sun, price for the use: dynamic mean of 24 h, static the cheapest window price, else the work price). `BatteryPlan::decide()` is pure: per quarter hour from the window to 24 h after it (sun from the hourly forecast, house from the usual hourly profile, quarters `[t, pv, house, battery ct, house ct]` from `BatteryPlan::quarters()`, unknown prices from the day before) it tries target levels in 0.25 kWh steps (charge once to the level, the house pays its own price) and keeps the cheapest: grid import in and after the window minus export, with `grid_efficiency_pct` and `grid_wear_ct` per stored kWh; reasons `charge`, `sun`, `price`, `full` or `unknown`, with `end_soc` at the window end. `days()` gives the outlook table: per day the sun (forecast, today the rest), the house (usual profile) and, with `stored_kwh`, `total_kwh` and `floor_soc`, a quarter-hour simulation from what is stored now: usable energy above the backup buffer at the start, balance (start + sun − house), export when full, import when empty down to the buffer, and the end, which starts the next day (sun shaped by the hourly forecast and scaled to the day's total, no losses). `floorSoc()` is the backup buffer: `battery_strategy.backup_soc`, else the reserve entity's value, else 0. How it switches is universal (`BatteryPlan::steps($cfg, $index)`, also the step preview under Einstellungen → Speicher): an optional mode select `mapping.battery_operating_mode` (option `battery_strategy.grid_mode_on`, empty = by meaning `manual`, e.g. „manual“ or Sungrow „Forced mode“; `grid_mode_off`, empty = the mode from before), the power number `mapping.battery_force_charge` (W or kW by its unit, rounded to its step, within its min/max; `grid_kw`, else the discharge power, else 2.5 kW) and an optional command select `mapping.battery_charge_command` (`grid_cmd_on`/`grid_cmd_off`, by meaning `charge`/`stop`, e.g. Sungrow „Forced charge“/„Stop (default)“); `choose()` takes the chosen option if the entity has it, else the one by meaning (`MODES`); `steps()['error']` feeds `blocker()`. `sync()` (recorder, demo `/api/live`, master switch off, saving a plan) starts inside a planned run with mode, power, command and stops at the target, at the run end or when EMS is switched off with command, power 0, mode back, using the entities stored at the start (`mode_entity`, `power_entity`, `cmd_entity`, `restore`, `cmd_restore`). State, errors (retry after 60 s) and log in `kv.battery_grid`. `blocker()` says why it cannot switch (entities unmapped or unavailable). The demo has both entities and follows them.

The house load for the outlook, the battery plan, the energy flow and the charge plan is the usual day without wallbox: `Series::houseProfile()` (cached in `kv.house_mean`) takes 30 days of hourly HA statistics, subtracts the wallbox (its statistics, else the sessions spread over their charging time) and keeps per hour of day the median (`Energy::houseProfile()`), so days with charging before the wallbox was measured do not count; `houseMean()` is its mean. `snap.house_profile` carries the 24 values.

**Statistik:** `Heatmap` (`app/src/Heatmap.php`) serves `/api/series?chart=heatmap`; the page `views/statistik.php` is a GET filter form (metric, span, raster, from/to) plus prev/next links (`Heatmap::query()`), and `components/heatmap.js` draws the cells. `params()` normalizes the filters (an anchor from another span carries over: `2025-10` becomes year 2025), `range()` returns layout (`hours`, `calendar`, `matrix` for days × hours in a month or a custom range up to 62 days, `years`), bucket period (hour, day, month), window and title. Values per local slot key (`Y-m-d H`, `Y-m-d`, `Y-m`): power and SOC from HA long-term statistics (mean × bucket hours, the running bucket only up to now; `pv_energy` change when mapped; signed grid/battery split by sign), charging from `sessions` spread uniformly over start + `duration_s` (a Ladevorgang counts where its first cycle starts), forecast from `forecast_days` (hours from the radiation model scaled to the day), DWD weather from `weather_hours` or, for older days, the last `forecast_issues` run before the day ended. Ratios (Autarkie, Eigenverbrauch, Sonnenanteil, Güte) come from sums, not means. Cells carry `v` (0…1 intensity), `t` (text with unit) and `n` (short number); the script picks black or white ink from the cell's computed background luminance (`--hm-ink-dark`, `--hm-ink-light`).

**Tariff and electricity price:** `Tariff` holds both tariffs in one record (`tariffs`: `mode` static or dynamic; static `import_ct` and `base_eur` gross, optional `windows` (at most `WINDOWS_MAX` 6: `from`, `to`, `days` 1–7 with [] meaning all, `for` ⊆ `Tariff::USES` car/battery, `kind` minus or price, `ct` gross; `staticWindows()` cleans them, `windowAt($t, $ts, $use)` finds the cheapest matching one, a window over midnight belongs to the weekday it starts, `windowCt()`, `staticCt($t, $ts, $use)`; `importCt($ts, $use)` and `averageImportCt(…, $use)` take `house`, `car` or `battery`, sessions are priced as `car`, `BatteryPlan::quarters()` as `battery`, `ChargePlan::refresh()` as `car`), `mapping.price_static` can deliver `import_ct` (`syncStaticPrice()` in the recorder every 5 min writes a change from today into the history; saving the form takes the entity's value); dynamic `dyn_grid_ct`, `dyn_levies_ct`, `dyn_supplier_ct` net ct/kWh, `dyn_vat_pct`, `dyn_base_eur`, optional `dyn_windows` for §14a module 3 grid fees, up to three, may wrap midnight; `export_ct` fixed EEG; `co2_g_kwh`), so the statistics can price every time in both. Every change is saved with a valid-from date in `kv.tariff_history` (`Tariff::withEntry()`; `saveHistory()` keeps `kv.tariffs` on the record valid today); without history the current record applies since `Tariff::ORIGIN`. `Tariff::at()` picks the record of a time, `parts()`/`dynamicCt()` give the end price (spot + grid + levies + supplier) × (1 + VAT), `dynamicAt()` prefers recorded provider prices, `importCt()` follows the active mode, and `forRow()` prices a session (time-weighted over its charging time). `MarketPrices` fetches Energy-Charts (`/price?bzn=DE-LU&start&end`, end inclusive; aWATTar as fallback, which only fills hours without quarter hours) for today and from 13:00 for tomorrow (retry every 15 min), and backfills two years in 31-day chunks; its source line `MarketPrices::SOURCE` must stay visible (CC BY 4.0). `GridMeter` integrates grid power per quarter hour, and `merge()` prefers measured hours over HA hourly statistics (`Heatmap::importHours()`, fetched month by month for the cache). `PriceView` builds Prognose → Strompreis, only for the active tariff: dynamic now, today, tomorrow, the charging windows and the cheapest and dearest hour; static the work price, `static_uses` (per use with a window the price now and the next change) and `static_windows` (grouped by time, with prices); `chart=price` carries only the active tariff's series (dynamic: `dynamic`, `spot`, `export`; static: `static`, `car`/`battery` when windows exist, `export`, up to tomorrow midnight). Einstellungen → Tarif shows only the active tariff's fields (`[data-tariff-panel]`, CSS `:has()`), the static windows as cards (`swin[i][…]`, one empty card to add, `components/tariff.js` computes the window price while typing); the other tariff's fields stay in the form. The yearly check below is `YearCheck`. `Tariff::parseEntity()` reads provider entities generically (lists with start and price in the attributes, unit from `unit_of_measurement`); it is untested against real Tibber or Octopus data. Session costs everywhere go through `Tariff::forRow()` (`Sessions::summary()` and `chart()` take an optional `Tariff`), the heatmap's `import_cost`, `export_pay` and price metrics use the record valid at each hour, and `Snapshot` carries `price` (`Tariff::now()`) for the energy flow and the live payload. 

`YearCheck` builds „Welcher Tarif lohnt sich?“ (static, static with the tariff's time windows when it has some, dynamic) (route `/prognose/strompreis`, inputs `haus`, `km`, `verbrauch` and `auto` (`CAR_MODES`: `sonne` takes PV surplus first, `fenster` charges only in the window) in the query, suggested by `suggest()` from the house profile, the odometer or energy of the sessions and the car's consumption; the heatmap's `kennzahl` radios belong to the form through `form="decide-form"`, so „Neu rechnen“ keeps the metric). `days()` caches the last 365 days of prices (hourly means, day mean, cheapest window of `length_h`) with today's tariff in `kv.year_prices`. `pv()` reads the plant's yield from PVGIS (`seriescalc` hourly for the weather year `plant.pvgis_year`, default 2023, v5.2 as fallback up to 2020; else `PVcalc` monthly; else 950 kWh/kWp spread over the year) with the losses `plant.pvgis_loss` (default 14 %); only the recorder fetches (`pv(…, true)`, cached half a year in `kv.pvgis` under a key of all parameters, errors retried after a day), the page never waits for it. `location()` is `plant.lat`/`plant.lon` when both are set, else `HaSource::coordinates()` (HA `/api/config`, cached a day in `kv.ha_location`). Einstellungen → Prognose shows `status()` and saves `section=pvgis` (location, losses, weather year; `do=refresh` calls `forget()`, so the recorder fetches again). The battery counts only above the backup buffer (`BatteryPlan::floorSoc()`). `simulate()` is pure: hour by hour the car takes PV surplus first (not with `fenster`), the battery the rest and covers the evening and night, never across weeks; the grid covers the rest, statically at the work price, dynamically the house at the hour's price and the car in the window up to `length_h × car_kw` a day (the rest at the day mean), and the battery pre-charges the house's grid import in the window where that beats losses and wear. Days without prices use `typicalDay()` (mean hourly profile of the priced days) instead of scaling up the priced ones. It returns per ISO week `day`, `window`, `save` (static minus window, ct/kWh), `sun` (kWh) and `cover` (%), rendered as a server-side heatmap grouped by quarter (KW 1–13, 14–26, 27–39, 40–53) with all metrics in `data-v-*`/`data-n-*`/`data-t-*` and legend values in `data-metrics` that `components/weekmap.js` switches (ink from `heatmap.js`), and the year with work price and base fees apart (`static_energy_eur`, `static_base_eur`, …; feed-in left out because it is the same in all). The third variant comes from `windowPlan()` (per use and weekday the windows as [hours, ct], cheapest first): the car's grid need in its windows up to `car_kw × hours`, the battery pre-charging the house's grid import in its windows where `ct / efficiency + wear` beats the work price (`windows_energy_eur`, `windows_eur`, `windows_car_kwh`, `windows_shift_kwh`, `has_windows`).

**PV forecast:** `WeatherFeed` downloads the DWD MOSMIX KMZ for station F9519, refetching every 30 min, and on the next recorder tick after a failure. `Rad1h` is kJ/m² per hour; divide by 3.6 for W/m². `Forecast::powerKw()` computes kWp × constants × factor, capped at the inverter. `Series::calibrate()` (also called from `Series::days()`) sets `plant.factor` to the mean of actual/model, reset to 0.93 with fewer than 5 days. ## Conventions and gotchas

- UI text, code comments and commit messages are German; identifiers are English. Commit messages are full German sentences with no type prefix.
- Never name evcc in anything a user sees (views, messages, logs, notifications, README); code comments may point to its source for parity.
- Format numbers with `num()`, `kw()`, `kwh()`, `pct()`, `ct()` or `euro()`: decimal comma and a narrow no-break space (`NNBSP`, U+202F) before the unit. `kw()` shows one decimal; the control details show two. Input fields use `ui_field_num()`, which has no thousands separator, because `post_float()` would read `1.500` as 1.5.
- Every link goes through `url()`, which adds the HA Ingress prefix from `X-Ingress-Path`. JavaScript reads it from `data-base` on `<html>` (`base()` in `core/dom.js`).
- CSP is `default-src 'self'` plus a hash for one inline style. No inline scripts, no `style` attributes, no external resources. Proportions travel as `data-*` attributes and JavaScript sets them through CSSOM (`el.style.setProperty`).
- The view transition opt-in (`VIEW_TRANSITION_CSS` in `helpers.php`) sits inline in the head of `shell.php`, because Chrome reads it when `<body>` is inserted, often before `app.css` has loaded. Any output before `<!doctype html>`, such as a PHP warning, puts the page into quirks mode and aborts the transition with "ViewTransition opt-in disabled".
- Every POST handler calls `csrf_check()`, and every POST form includes `csrf_field()`.
- A new page needs a view, a branch in `index.php`, and an entry in `$nav` in `shell.php` (with a short label if the name does not fit 72 px at 360 px).
- A new setting needs a default in `ConfigStore::defaults()` and handling in `Actions::saveSettings()`. Add it to `portable()`/`applyPortable()` if it should survive JSON export and import.
- `icon('x')` references `#x` in the sprite. New Lucide names go into the list in `bin/build.mjs`, followed by a rebuild. `app/assets/icons/battery.svg` is hand-drawn.
- Live values: `core/live.js` polls `/api/live` every 5 s only if the page has `[data-live]`, `[data-live-num]` or a live component. `data-live` takes a dot path into the payload (`battery.soc_text`); a path that does not exist is silently skipped.
- Changing `$version` in `Series::calibrate()` forces one recalibration.
- Every page load and every `/api/live` poll runs `Snapshot::build()`. That writes forecast rows and the house-mean cache, and can download the DWD file. Reads have side effects. In demo mode `/api/live` also ticks sessions, the controller, the backup buffer, the notifications, the grid meter and the market prices (`DemoModel::marketPrices()`, no network), because no recorder runs. Demo notifications only go to the log; `demo-seed.php` seeds a year of prices and a tariff history.
- `Series::repairKnownDays()` is a one-off repair with hard-coded dates in 2026-10, guarded by `kv.model_repair`. It is the only code that sets `model_mode` to `pin` or `drop`.
- The plant and tariff defaults in `ConfigStore::defaults()` (10.03 kWp, azimuth 270, tilt 13, 10 kW inverter, 34.7 / 11.0 ct) describe the author's system.
- `.env` and `data/` are gitignored. Never commit the token.
